## Behavioral explanation
A one-command specialization of the generic DBC send stub `FUN_0017f948`
(`dbc_rpc_send`). It packs two caller-supplied blobs, each with its own length
word, into a fixed **40-byte (`0x28`)** message and transmits it as DBC command
**`0x0103400b`** to the IOP `dbcman` module via `sceSifCallRpc`
(function `0x8000131b`, client-data `0x27afb0`, guarded by semaphore
`uRam0027e540`).

Message layout built on the stack at `&uStack_a0`:

```
offset  size  field                    source
0x00     4    len_b   (u32)            param_2
0x04     4    len_a   (u32)            param_4
0x08   len_a  blob_a                   memcpy(param_5, len_a)
0x08+  len_b  blob_b  (@ 0x08+len_a)   memcpy(param_3, len_b)
------  -----
total  0x28   (8 header + 32 data)  — the fixed length handed to dbc_rpc_send
```

Note the header order is `[len_b, len_a]` while the payload order is
`[blob_a, blob_b]` (the two length fields are cross-ordered relative to the data),
faithfully reproduced below. Only `0x28` bytes are sent, so `len_a + len_b` must
be `<= 32` to fit the 32-byte data window.

This is DBC transport under the SN@P/session layer, not a SN@P app-opcode emitter.
