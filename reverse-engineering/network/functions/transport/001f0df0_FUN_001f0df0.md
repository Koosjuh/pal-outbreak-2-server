## Behavioral explanation
Synchronous SN@P-IPC **list query**. Given a category selector `param_2` in 0..4, it fetches an array
of fixed-size **0x30c-byte (780) records** from the IOP SN@P module (library call **fno 0x4e**) and
copies them into the caller's buffer. The reply status word (RX+0x18) doubles as the **returned
record count**: if negative the call failed (returns 0xffff); otherwise `count * 0x30c` bytes are
copied from RX+0x20 to `param_1` and the count is returned. The recv size 0xc54 accommodates up to 4
records (4 * 0x30c = 0xc30, + 0x20-byte header ≈ 0xc50). This is the "enumerate a small table"
operation — a strong candidate for a room-list or member/roster fetch keyed by category.

## Input / output
- `param_1` — out buffer; receives `count` contiguous 0x30c-byte records.
- `param_2` — category/type selector, **must be < 5** (guarded); the low word is sent at tx+0x1c.
- **Returns** `u16`: the record count (>=0) on success, `0xffff` if `param_2 >= 5` or the IOP returned
  a negative count/error.

## Side effects
- `uRam0037cf1c = (u32)param_2`.
- Blocking SIF RPC (fno 0x4e, send 0xc54 / recv 0xc54) to the IOP SN@P module.
- On success: `memcpy(param_1, RX+0x20, count*0x30c)` (FUN_001069a8).
- Acquires the SN@P IPC mutex; **releases it (ef3f0) only on the success path** — see uncertainty.

## Important branches
- `param_2 >= 5` -> return 0xffff **without** issuing the RPC (input gate).
- After RPC, `iRam0037bf18 < 0` (negative count) -> return 0xffff (IOP-side error/empty-error).
- Else -> copy `count*0x30c` bytes, unlock, return count.

## Constants & flags
- `0x4e` — SN@P IOP library selector. `0x30c` (780) — per-record stride. Max 4 records per call.
- `0xc54` — TX/RX size. Category domain 0..4 (5 categories).
- `0xffff` — error/invalid sentinel return.

## Corrected reconstruction
```c
// Enumerate up to 4 fixed 0x30c-byte records for a category (IOP library call 0x4e).
// Returns record count, or 0xffff on bad category / IOP error.
uint16_t snap_req_fn4e_list_records(void *out /*count*0x30c*/, long category /*0..4*/) { // [inferred]
    snap_ipc_lock();                                 // FUN_001ef3e0
    uint16_t ret = 0xffff;
    if (category < 5) {
        *(uint32_t *)&snap_ipc_tx[0x1c] = (uint32_t)category;   // uRam0037cf1c
        snap_ipc_call_rpc(0x4e, snap_ipc_tx, 0xc54,            // FUN_001ef400
                                snap_ipc_rx, 0xc54);
        int count = *(int *)&snap_ipc_rx[0x18];                // count doubles as status
        if (count < 0) {
            ret = 0xffff;
        } else {
            memcpy(out, &snap_ipc_rx[0x20], count * 0x30c);    // FUN_001069a8
            snap_ipc_unlock();                                 // FUN_001ef3f0 (success path only)
            ret = (uint16_t)count;
        }
    }
    return ret;
}
```

## Remaining uncertainty
- The decompile shows `snap_ipc_lock` on entry but `snap_ipc_unlock` **only inside the success branch**
  (the `param_2>=5` early-return and the `count<0` branch skip ef3f0). This is either a decompiler
  artifact (unlock hoisted/duplicated at other returns) or a genuine mutex-leak on the error paths —
  worth a targeted re-check against the raw MIPS. Flagged, not asserted.
- Record identity (room vs member vs some roster) and the 5 category values are undetermined; 0x30c
  (780) bytes is a large per-entry struct. Medium overall.
