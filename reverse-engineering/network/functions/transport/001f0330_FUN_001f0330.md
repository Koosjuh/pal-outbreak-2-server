## Behavioral explanation
The **largest** SN@P RPC stub — **selector `0x21`**, a compound request of `0x524` bytes. It marshals
three scalar ints (`param_8/9/10` → req `+0x00/+0x04/+0x08`), a 16-bit id (`param_1` → `+0x1c`) and a
16-bit length/count (`param_2` → `+0x1e`), then copies **five 256-byte data blocks** (`param_3..7`)
into consecutive request slots via `FUN_00109eb8`. The five 0x100 blocks are the room's text/metadata
fields (name, password, comment/description, and member/config payloads) — this is the EE→IOP submit of
a **create/enter-room** request. Returns the module status word.

The `0x524` request size = header (`0x24`) + 5×`0x100` (`0x500`) = `0x524`, confirming the five-block
layout.

- **param_2** (`u16`): length/count → req `+0x1e`.
- **param_3..param_7** (`void*`, 5×): 256-byte blocks → req `+0x20`,`+0x120`,`+0x220`,`+0x320`,`+0x420`.

- **Return** (`u16`): SN@P status word (`0x37bf18`).
